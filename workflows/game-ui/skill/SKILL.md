# 游戏UI界面（game-ui）

## 这条工作流产出什么

`游戏系统需求（文本）→ 策划案生成（文本）→ UI界面拆分（每屏一条提示词）→ UI界面生成（每屏两张图）`

- **策划案**：一份可读的系统策划案正文，存在「策划案生成」节点与文本图库里。
- **界面提示词**：每屏一条带字 `prompt` + 一条空字 `cleanPrompt`，存在「UI界面拆分」节点的图库与 `uiScreens` 里。
- **界面图**：每屏**两张** —— 带字精修图 + **空字底图**（无任何可读文字，供引擎叠本地化文字）。统一 **9:16**、统一由全局 UI 风格参考图控制画风。
- 上限：**最多 12 屏**（`UI_SPLIT_SLOT_CAP`），超出的屏会被丢弃。

## 什么时候用 / 什么时候别用

用：用户要**游戏界面资产**（HUD、背包、任务、公会、弹窗、列表…），或手里有一份系统策划案需要落成界面图。

别用（用兄弟工作流）：

| 用户其实想要 | 该用 |
|---|---|
| 游戏**图标**（技能/道具/装备图标，要整版切格打包） | `game-icons`（游戏图标包） |
| 游戏买量短视频素材 | `game-ua-video`（游戏买量） |
| 角色设定立绘 / 多视角 | `character-sheet`（角色设定） |
| 电商主视觉、变体矩阵 | `ecom-ad-deep`（电商带货） |

**易错点**：`game-ui` 出的是**整套界面图**（每屏双轨、统一控件体系），不是图标包，也不是"UI 概念图一张"。

## 上游输入怎么给

用户必须给的是**游戏系统需求**，写进「策划案生成」节点（`asset.gameSystem`）的 `text`：

- 建议写：要哪几个系统（背包 / 任务 / 公会…）、每个系统的功能点、有哪些界面与状态。
- 预设里是占位符 `（在此填写游戏系统需求，如：背包系统、任务系统、公会系统…）`。
- **两种进入方式**：
  - `text` 留空 / 只有一句话 → 节点按默认系统提示词调文本模型**扩写**成完整策划案。
  - `text` 直接写成完整策划案正文 → 节点把它当**底稿扩写**，不会推翻你的结论（`text` 就是上次生成产物时会跳过并入，保持"重新生成"语义）。适合 agent 自己先写好策划案正文再写进 `text`。
- 想改拆分口径时，改「UI界面拆分」节点的 `generateInstruction`（用户指令）或 `generateSystemPrompt`（系统提示词），不要去改 `uiScreens`。

**风格不来自文案**：界面的视觉风格一律由**全局风格参考图（风格库 → UI 风格）**决定。拆分用的系统提示词会**主动剔除**策划案里的风格 / 材质 / 光影 / 配色描述（科幻、赛博、写实、卡通、金属、玻璃、发光…都是违禁词）。所以：
- 不要在策划案或拆分指令里写画风词，写了会被剔除，白费；
- 要改画风就去换/新增**风格参考图**，再重跑生成。

## 关键约束与顺序

1. **顺序必须按 策划案 → UI拆分 → UI生成 走**。`ui.split` 的 `in` 是要有上游正文的（`generateInstruction` 里带 `@` 引用时可以只靠指令），`ui.gen` 的 `in` 是 `texts` 数组 —— 上游没跑，链子就断在那里。
2. **类型是严格对应的，不要乱接**：`ui.split` 的 `in` 是 `text`、`out` 是 `texts`；`ui.gen` 的 `in` 是 `texts`、`out` 是 `images`。想直接把某张图接进 `ui.gen` 是不行的。
3. **生成分两步，中间必须进内图**：`ui.gen` 只做两件事 —— 把上游 `texts` 收成 `uiScreens`，以及 **cook 时收集内图的全部输出边界**。真正的出图发生在**双击节点进入的内图**里（每屏一条带字轨 + 一条空字轨）。流程是：
   1. 跑「策划案生成」→ 跑「UI界面拆分」；
   2. **双击「UI界面生成」进入内图，逐屏出图**；
   3. 回外层 **cook**「UI界面生成」，把内图各屏输出汇集成 `images` 出口。
   跳过第 2 步直接 cook，只会拿到空图片组 —— 不是报错，是"成功的空结果"，最容易误判。
4. **不要直接改 `uiScreens`**。提示词变化（或内图结构版本变化）会让节点作废 `uiSplitAssetId`，下次进内图**整图重建**。要改界面列表就改拆分节点的指令并**重跑拆分**。
5. **内图上限 12 屏**（`UI_SPLIT_SLOT_CAP`），策划案里系统太多时先让用户砍到 12 屏以内，否则后面几屏静默丢失。
6. **拆分结果必须是 JSON 数组**（每项 `id`/`title`/`prompt`/`cleanPrompt`）。模型输出 markdown 列表时解析器会兜底逐行转条目，但会缺 `cleanPrompt`（由 `buildTextlessUiPrompt` 派生），质量明显更差 —— 不要主动引导它输出 markdown。
7. **每屏两张图是设计意图，不是重复生成**：空字底图供引擎叠本地化文字，绕开 AI 像素文字的乱码问题。空字轨默认**以本屏带字图为参考图**去字，两条轨布局才会一致。
8. 文字生成需要文本模型；`ui.split` 没有文本模型时会退化为"从指令/上游正文里解析界面"，结果通常不是你要的。

## 常见追问怎么答

- **"能出超过 12 屏吗？"** 单次不行，上限 12 屏。要做更多，分两批（拆两次、生成两次）或把相关界面合并成一屏。
- **"图上的字是乱码 / 想让文字可改"** 用**空字底图**那一轨，自己在引擎里叠文字。带字版的可读性由图像模型决定，工作流不保证文本正确。
- **"怎么改画风？"** 换全局风格参考图（风格库 → UI 风格），再重跑生成。写进提示词的画风词会被拆分提示词剔除。
- **"能直接拿到每个界面的 PNG 吗？"** 能。内图每屏有两个输出边界（带字 / 空字），cook 后汇总在 `ui.gen` 的 `out`（`images`）与节点图库里。
- **"界面尺寸能改吗？"** 内图生成节点固定写了 9:16（UI 界面竖屏口径）；要别的比例得进内图改那些图像生成节点，本条工作流不提供外层开关。**需自行确认**目标模型是否支持该比例。
- **"能让 agent 全自动跑完吗？"** 拆分与生成可以（跑节点 / 任务），但"进内图逐屏出图"这一步当前需要人在应用界面里操作；外层 cook 之后才可以继续自动化。不要承诺全流程无人值守。

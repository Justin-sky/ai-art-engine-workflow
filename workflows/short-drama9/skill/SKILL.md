# 短剧分镜·9格直出（short-drama9，36 节点 / 51 连线）

## 这条工作流产出什么

```
剧本 → 节拍拆解表 → 9宫格分镜表 → 1 张 9宫格拼图 → 9 格锚点图
     → 动画师·9宫格动态提示词表（9 条，每条 3~15 秒）
     → 9 条动态视频（每条直接以对应 9宫格锚点图为首帧参考）
```

最终产物是 **9 条动态视频**。它是 short-drama 的"直出"变体：**跳过 4宫格展开**，一个宫格直接对应一条视频，靠"一条视频覆盖一段完整剧情"换回镜头数量上的损失。

图里有一个 `note.text` 便签「流水线说明」，写的就是这条链与审核约定。

## 开跑之前：先把成本讲清楚

| 环节 | 模型调用 | 说明 |
|---|---|---|
| 3 个生成阶段（节拍拆解 / 9宫格 / 动态提示词） | 3 次文本模型 | 提示词很长（要一次产出 9 条 3~15 秒的时间轴） |
| 3 个导演审核 | 3 次文本模型 | 逐项打分 + PASS/FAIL |
| 1 张 9宫格拼图 | 1 次图片模型 | |
| 9 条动态视频 | **9 次视频模型** | 最贵的一环，按你的提供商规则计费 |
| 9 次宫格裁切 + 9 次动态格选择 | 0 次模型调用 | 纯本地裁切 / 纯文本选取 |

- 比 36 条版便宜在**调用次数（9 次 vs 36 次）**，不是"总秒数"：预设 9 条 × 15 秒 ≈ 36 条 × 4 秒。若你的提供商按秒计费，两者同量级。
- 每条视频的时长是**模型生成的**（提示词要求按信息量在 3~15 秒里选），节点上的 `generateDuration: 15` 只是上限请求，最终会被所选视频模型的时长档 clamp。
- 视频是**异步长任务**（提交后由应用轮询），9 条同属拓扑最后一层、会被**并行提交**。
- 每条视频要在一镜内吃完「上一关键帧到本关键帧」的全部剧情与对白，**信息密度很高**：9 格版更容易出现"动作糊在一起 / 台词被吞"。要镜头节奏就上 36 条版。

## 什么时候用 / 什么时候别用

**用**：想先看效果、成本敏感、或成片素材只需要 9 个关键节点；剧本节奏本身是"每场一个长镜头"。

**别用**：

- 要细密镜头语言（定场/引入/冲突/收尾 4 拍推进）→ **short-drama**（137 节点、36 条视频）。
- 已经有分镜图、只想串成片 → **storyboard-video**。
- 只要一张九宫格图或一条视频 → 直接用 `generate_image` / `generate_video`，不要落整条流水线。
- 需要多集连拍 → 一次一集，见下。

## 上游输入怎么给

- 剧本写在 `play.script` 节点（安装后标题是「剧本」）的 `text` 参数里。**出厂值是占位符**「（在此填写单集剧本，或用「短剧创作框架」先生成）」，不替换就直接跑 = 拿占位符生成。
- **一次一集**。装进工程后所有流水线节点的 `episodeScopeKey` 会被应用改写成**宿主资产 id**，审核状态与产物命名都按它隔离 → 第 2 集请**再落一份资产**，不要在同一个资产里换剧本硬跑（完成的节点不会被重跑）。
- 9 格版对剧本的要求比 36 格版更高：动态提示词阶段要拿**完整剧本 + 拆解表 + 9宫格表**，把每个区间的剧情、动作、台词、情绪转折**全部逐字写进对应那条视频的时间轴**。所以剧本必须**对白明确（带说话人）**、情绪转折可定位；含糊的剧本会变成 9 条都在"泛泛地演"。

## 关键约束与顺序

### 阶段顺序是固定的

```
剧本 → 节拍拆解表 →(+review1) 9宫格分镜表 →(+review2)
     → 9宫格拼图 → 9 格锚点图
     → 动态提示词表 →(+review4) → 9 条视频
```

- **动态提示词阶段要用到剧本 + 拆解表 + 9宫格表三者**（图上是三条边进同一个 `in`）：拆解表提供"每格必须覆盖的节拍区间"，剧本提供逐字对白。缺任何一条边，9 条视频就会漏剧情。
- **9 格锚点图必须在动态提示词之前/同时就位**：每条视频的参考图是「宫格提取·格N」，没有它视频就没有画面基准。

### 不能跳「节拍拆解表」

1. **9宫格阶段**：应用会解析拆解表、按情绪强度选出 9 个锚点，把「锚点1 ↔ 格1 … 锚点9 ↔ 格9」自动注入提示词。没有拆解表 → 没有锚点注入 → 模型自己乱选 9 格。
2. **动态提示词阶段**：应用会注入「每格必须覆盖的节拍区间」：
   - 格1 = 剧本开头 → 锚点1；
   - 格N = 上一锚点之后 → 锚点N；
   - **格9 = 上一锚点之后 → 拆解表最后一条**，即末端关键帧之后直到剧本结束的剩余节拍也要塞进第 9 条，**禁止停在最后一个关键帧**。

   没有拆解表就没有这段注入 → 第 9 条视频会在高潮处截断，结局丢失。
3. **审核**：拆解表是 review1 的审核对象，状态机从 breakdown 阶段起步。

### 两张表的格式是硬契约（解析器是正则）

解析失败**不报错**，只静默退化。

- **节拍拆解表**：Markdown 表格，5 列固定为 `| 节拍编号 | 事件摘要 | 观众获得 (信息/情绪) | 情绪强度 (1-10) | 关键锚点 (是/否) |`；编号可写 `1` 或 `#1`；**最后一列必须恰好是「是」或「否」**。整表 12~28 条节拍，其中 9 个锚点（可按篇幅 ±2）。
- **9宫格分镜表**：每格一个二级标题 `## 格1 [节拍ID: #1] - 标题`，必须是 `## 格N`（N = 锚点序号 1~9）。每格必须写「景别与视角 / 人物动作与表情 / 场景与光影 / 构图与动线 / 故事功能」；服装、道具、场景、发型**只写名称**，外观细节留给参考图。
- **动态提示词表**：每条一个标题 `## 镜头N [来源: 9宫格 格N]`。**这个来源标记是每条视频能拿到自己那条提示词的唯一依据**：解析器把「9宫格 格N」读成 (组=N, 格=1)，正好对上第 N 个动态格选择节点。标记丢了 → 解析出的组号会串位 → 绝大多数格取不到自己的提示词，退化成**整张表透传**（9 条视频共用同一段文字，钱花了片子全一样）。
- **审核结论**：单独一行 `## 结论: PASS` 或 `## 结论: FAIL (原因: …)`；解析不到就不写状态。
- 每条动态提示词必须自带字段：时长（3~15 整数秒）、一句话概述、时间轴剧情（0 秒起连续覆盖、不重叠不留空）、镜头运动、环境/灯光、音频、全局锁定；对白写进对应秒段（`说话人+语气："台词"`），无对白写「无对白」。

### 宫格索引（1-based，行优先）

| 位置 | 参数 | 取值 |
|---|---|---|
| 9宫格提取节点（格 N） | `anchorCellIndex` | `1`~`9` |
| 9宫格提取节点的裁切框 | `imageGridSplit` | `{rows:3, cols:3, selected:["行-列"]}` |
| 动态格选择节点（第 G 条提示词） | `cellGroupIndex` + `cellIndex` | `G`（1~9） + `1` |
| 动态视频节点（第 G 条） | `motionCellIndex` | `"G-1"` |

行优先映射：格1=1-1、格2=1-2、格3=1-3、格4=2-1、格5=2-2、格6=2-3、格7=3-1、格8=3-2、格9=3-3。

**注意 9 格版的 `cellIndex` 永远是 1**（一条提示词一格视频），不要照抄 36 格版的 1~4。

### 审核怎么用

- 三个审核节点（review1 节拍 / review2 9宫格 / review4 动态提示词）把结论写进审核状态文件：**PASS → 推进；FAIL → 回滚到该阶段并记下原因**。review4 在细节上用的是 9 格版审核提示词（带上这个变体，检查项里含"最后一格必须覆盖到剧本结束"）。
- 重跑该阶段节点时，**最近一次 FAIL 原因会被自动追加进提示词**。
- 正确返工 = 重跑被 FAIL 的那个阶段节点。**不要手改审核节点的文本冒充 PASS**：状态机只在审核节点真正执行时才写文件。

## 怎么操作（MCP 路径）

1. `workflow_list_installed` 确认 id；`workflow_use_installed({ id:"short-drama9", name?, generateAspectRatio?, imageModel?, videoModel? })` 落盘为工程资产，得到 `assetId`（竖屏一般传 `9:16`）。
2. `graph_read({ assetId, includeParams:true })` 找到标题为「剧本」的节点 id。**不要假设节点 id 等于 workflow.json 里的 key**，物化时是随机 id。
3. `graph_edit({ assetId, ops:[{ op:"node_update", nodeId, params:{ text:"<剧本全文>" } }] })` 写剧本；同批 ops 里统一各生成节点的 `generateModel` / `generateAspectRatio`。
4. `task_run({ assetId })` → `mcpTaskId`；`task_status({ mcpTaskId })` 轮询到 done / error。**`task_run` 按整图跑**，并且**会复用已完成的节点**。
5. 汇报：给出 9 条视频路径，并说明哪几格失败、哪几条对白可能缺失。

**细粒度控制不在 MCP 里**：让用户打开该资产，点顶部工具栏的「剧集流水线」按钮。那里有「生成9宫格拼图」「生成9宫格动态提示词」、每阶段的「重新生成」「导演审核」，以及每格的「生成这条视频」。打开前该资产至少要跑过一次节拍拆解，否则视图是空的。

## 重跑与返工（最容易踩的坑）

- `task_run` **会跳过状态为 done 的节点**。改完参数直接 `task_run` 通常什么都不发生（失败/未跑的会被补跑，已成功的不会重跑）。这是省钱的默认行为，不是 bug。
- 强制重跑某阶段：在「剧集流水线」视图点该阶段的「**重新生成**」。它会强制重跑该阶段节点，并把该阶段的**全部下游产物（拼图 / 提取 / 视频 / 审核）一并作废**，之后补跑才一致。
- 只重跑一条视频：选中该格 → 「重新生成这条视频」，只重跑那一个视频节点，上游复用。
- 画布上的整图「运行」**不跳过**已完成节点，会把整条链（含 9 条视频）重跑一遍 —— 别用它来"补跑"。
- 改了剧本或某个阶段的文本后，必须从该阶段往下整链失效重跑，否则下游与新文本不一致。

## 常见追问怎么答

- **「9 条够不够？」** 9 条等于 9 个段落各一镜，节奏靠一镜内部的推拉摇移；要切分镜头语言就上 short-drama（36 条）。
- **「时长不对 / 太短？」** 时长由模型按区间信息量生成，节点 `generateDuration: 15` 只是上限请求，会被模型时长档 clamp。太短通常是动态提示词里时间轴写得空泛 —— 改提示词要求再重跑该阶段。
- **「台词被吞了 / 没有对白？」** 动态提示词表必须逐字保留对白，并且审核会把"缺台词或改写"直接判 FAIL。看 review4 的 FAIL 原因，重跑动态提示词阶段。
- **「第 9 条缺结局？」** 这是最典型的漏：第 9 条必须覆盖末端关键帧之后直到剧本结束的剩余节拍。若拆解表没解析出来，节拍区间注入会失效 —— 先查拆解表格式（5 列、末列是/否），再重跑动态提示词阶段。
- **「参考图没锁住角色 / 为什么说是首帧？」** 视频的图从通用参考图口 `in-image` 进入（来自 9宫格锚点图），作为 image reference 送模型；节点指令里叫它「参考首帧」，那是文案。真正的首帧锁定需要模型声明支持 first_frame、`generateFrameMode` 设为 `first` 并改从首帧口接图（此模式下参考图会被弃用）—— 需自行确认模型能力。要锁外观，最有效的是给「9宫格拼图·锚点画布」的 `in-image` 接一张角色设定图（图里这个口是空着的，只接了文本）。
- **「审核 FAIL 了怎么办？」** 看流水线视图顶部的 FAIL 原因，重跑该阶段（原因自动进提示词）。格式类 FAIL 优先改提示词里的格式要求。
- **「多集怎么办？」** 一次一集；第 2 集再落一份资产。

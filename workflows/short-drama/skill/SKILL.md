# 短剧分镜（short-drama，137 节点 / 191 连线）

## 这条工作流产出什么

```
剧本 → 节拍拆解表 → 9宫格分镜表 → 1 张 9宫格拼图 → 9 格锚点图
     → 4宫格动态分镜表（9 组 × 4 格 = 36）→ 9 张 4宫格拼图 → 36 格提取图
     → 36 条动态提示词 → 36 条动态视频
```

最终产物是 **36 条动态视频**，每条以对应 4 宫格提取图为参考图。中间产物（4 张 Markdown 表 + 10 张拼图 + 45 张格图）都可以单独取用。

图里有一个 `note.text` 便签「流水线说明」，写的就是上面这条链与审核约定。

## 开跑之前：先把成本讲清楚

一次完整运行会真的调用模型。下面是按图上节点数点出来的，不是估算：

| 环节 | 模型调用 | 说明 |
|---|---|---|
| 4 个生成阶段（节拍拆解 / 9宫格 / 4宫格 / 动态提示词） | 4 次文本模型 | 每次一段长提示词 |
| 4 个导演审核 | 4 次文本模型 | 逐项打分 + PASS/FAIL |
| 1 张 9宫格拼图 + 9 张 4宫格拼图 | 10 次图片模型 | 每张拼图一次 |
| 36 条动态视频 | **36 次视频模型** | 最贵的一环，按你的提供商规则计费 |
| 45 次宫格裁切 + 36 次动态格选择 | 0 次模型调用 | 纯本地裁切 / 纯文本选取 |

- 视频是**异步长任务**（提交后由应用轮询）。36 条视频在拓扑上同属最后一层，会被**并行提交**，不是一条条排队 —— 开始前提醒用户注意提供商的并发与配额，中途可在应用的任务列表里停。
- 预设给每条视频写的是 **4 秒**，但最终时长由**所选视频模型的时长档决定**（不支持就被改写）。换模型前先确认它支持哪些时长。
- **不要把这条工作流当成"先试一下"的按钮**：点一次整图运行（或首次 `task_run`）就是 36 次视频调用。想先看效果、或成本敏感，先走 short-drama9。

## 什么时候用 / 什么时候别用

**用**：用户有一集完整剧本，要分镜 + 成片素材，且接受 36 次视频调用。镜头密度最高（每组 4 格：定场 / 引入 / 冲突 / 收尾）。

**别用**：

- 只想先看效果 → **short-drama9**（36 节点、9 条视频，一条视频吃掉 3~15 秒的完整剧情区间）。两者总时长量级接近（预设 36×4 秒 vs 9×15 秒），差别在**调用次数（36 vs 9）与镜头密度**，不在"哪个更省钱"这一句话上。
- 已经有分镜图、只想串成片 → **storyboard-video**（剧本文本 → 分镜图 → 视频；没有节拍表、宫格切分与审核）。
- 只要一张九宫格图、或只要一条视频 → 不要落整条流水线，直接用 `generate_image` / `generate_video`。
- 需要多集连拍 → 这条工作流一次只处理**一集**，见下。

## 上游输入怎么给

- 剧本写在 `play.script` 节点（安装后标题是「剧本」）的 `text` 参数里。**出厂值是占位符**「（在此填写单集剧本，或用「短剧创作框架」先生成）」，不替换就直接跑 = 拿占位符生成。
- **一次一集**。装进工程后，所有流水线节点的 `episodeScopeKey` 会被应用改写成**宿主资产 id**（不是预设里的 `ep01`），审核状态文件与产物文件名都按它隔离。所以第 2 集请**再落一份资产**，不要在同一个资产里换剧本硬跑（已完成的节点不会被重跑，见「重跑与返工」）。
- 什么样的剧本合适：单集、起承转合完整、对白用引号写清楚（动态提示词阶段要求**逐字保留对白**）。分镜阶段刻意不写外观细节（颜色 / 材质 / 形态留给参考图），所以剧本里对外观的描述不会进画面 —— 想要角色一致，靠参考图。
- 要做角色一致性：给「9宫格拼图·锚点画布」和「4宫格拼图·组G」的 `in-image` 参考图口接角色设定图。图里 9宫格拼图只接了文本、`in-image` 是空着的；4宫格拼图已经自动接了对应锚点图。

## 关键约束与顺序

### 阶段不能跳，尤其不能跳「节拍拆解表」

节拍拆解表不只是给人看的中间稿，它是后面两个阶段的**输入契约**：

1. **9宫格阶段**：应用会解析拆解表、按情绪强度选出 9 个锚点，把「锚点1 ↔ 格1、锚点2 ↔ 格2 …」自动注入提示词。没有拆解表 → 没有锚点注入 → 模型自己乱选 9 格，后面全部对不上。
2. **4宫格 / 动态提示词阶段**：应用会注入「每格必须覆盖的节拍区间」（格1 = 开头→锚点1；格N = 上一关键帧之后→锚点N；**末格 = 上一关键帧之后→拆解表最后一条**，含末端关键帧之后的剩余节拍）。这就是"最后一格不能停在关键帧、必须把结局写完"的机制来源。没有它，视频会漏结局。
3. **审核**：拆解表是 review1 的审核对象，状态机也从 breakdown 阶段起步。

所以：**不要为了让流程看起来更快而跳过或糊弄拆解表**，也不要手工重排锚点编号。

### 三张表的格式是硬契约（解析器是正则）

解析失败**不会报错**，只会静默退化成"原文透传"：锚点/节拍区间注入失效、动态格选择拿不到对应格。这是最值得盯的一处。

- **节拍拆解表**：Markdown 表格，5 列固定为 `| 节拍编号 | 事件摘要 | 观众获得 (信息/情绪) | 情绪强度 (1-10) | 关键锚点 (是/否) |`；编号可写 `1` 或 `#1`；**最后一列必须恰好是「是」或「否」**。列数、列序、末列写法错了 → 整表解析不出来。
- **9宫格分镜表**：每格一个二级标题 `## 格1 [节拍ID: #1] - 标题`，必须是 `## 格N`（N = 锚点序号 1~9），不是原始节拍编号。
- **4宫格动态分镜表**：`## 组N: 标题 -> 对应九宫格 格N`，组内四行必须是列表项 `- **格N-M (定场)**: 描述`（连字符、双星号、圆括号都要在）。
- **动态提示词表**：每条一个标题 `## 镜头N [来源: 4宫格 组x-格y]`。**这个来源标记是每格视频能拿到自己那条提示词的唯一依据**；缺了它，动态格选择找不到对应格会退化成「整张表透传」→ 36 条视频共用同一份提示词（钱花了，片子全一样）。
- **审核结论**：单独一行 `## 结论: PASS` 或 `## 结论: FAIL (原因: …)`；解析不到就不写状态。

### 宫格索引（1-based，行优先）

| 位置 | 参数 | 取值 |
|---|---|---|
| 9宫格提取节点（格 N） | `anchorCellIndex` | `1`~`9` |
| 9宫格提取节点的裁切框 | `imageGridSplit` | `{rows:3, cols:3, selected:["行-列"]}` |
| 4宫格提取节点（组G-格C） | `gridCellIndex` | `"G-C"`，如 `"2-3"` |
| 4宫格提取节点的裁切框 | `imageGridSplit` | `{rows:2, cols:2, selected:["行-列"]}` |
| 动态格选择节点 | `cellGroupIndex` + `cellIndex` | `1~9` + `1~4` |
| 动态视频节点 | `motionCellIndex` | `"G-C"` |

- 行优先映射：格1=1-1、格2=1-2、格3=1-3、格4=2-1 … 格9=3-3；4宫格内部 格1=左上(定场)、格2=右上(引入)、格3=左下(冲突)、格4=右下(收尾) → `"1-1"`/`"1-2"`/`"2-1"`/`"2-2"`。
- 9宫格格 N ↔ 4宫格组 N：4宫格拼图组 G 的参考图就是「宫格提取·格G」。
- **`anchorCellIndex` 与 `gridCellIndex` 是两个不同的参数名**（格选择节点上又是 `cellGroupIndex`/`cellIndex`）。写错不会被拒，但流水线视图会认不出这条格，只能回退按标题猜。
- 9宫格提取节点**不要**改成 `imageGridSplit.selected: []`（空数组 = 裁出全部格），那种节点每个只该裁出一格。

### 审核怎么用

- 四个审核节点把结论写进审核状态文件：**PASS → 推进阶段；FAIL → 回滚到该阶段并记下原因**。
- 重跑该阶段节点时，**最近一次 FAIL 原因会被自动追加进提示词**（只在该阶段最近一次结论是 FAIL 时，已 PASS 的历史 FAIL 不会再被附加）。
- FAIL 原因同时回标到审核节点与对应阶段节点上，流水线视图顶部直接显示。
- 正确返工 = 重跑被 FAIL 的那个阶段节点。**不要手改审核节点的文本冒充 PASS**：状态机只在审核节点真正执行时才写文件，手改不会推进阶段，而且下次执行就被覆盖。

## 怎么操作（MCP 路径）

1. `workflow_list_installed` 确认 id；`workflow_use_installed({ id:"short-drama", name?, generateAspectRatio?, imageModel?, videoModel? })` 落盘为工程资产，得到 `assetId`（竖屏短剧一般传 `9:16`）。
2. `graph_read({ assetId, includeParams:true })` 找到标题为「剧本」的节点 id。**不要假设节点 id 等于 workflow.json 里的 key** —— 物化时生成的是随机 id，必须读。
3. `graph_edit({ assetId, ops:[{ op:"node_update", nodeId, params:{ text:"<剧本全文>" } }] })` 写入剧本；同一批 ops 里顺手统一各生成节点的 `generateModel` / `generateAspectRatio`。
4. `task_run({ assetId })` → `mcpTaskId`；`task_status({ mcpTaskId })` 轮询到 done / error，产物相对路径在返回里。**`task_run` 按整图跑**（应用自己的描述是"整图按拓扑序执行生成"），并且会**复用已完成的节点**。
5. 汇报：给出录制/裁剪所需的每格视频路径，并说清哪几格失败。

**细粒度控制不在 MCP 里**：让用户打开该资产，点顶部工具栏的「剧集流水线」按钮（标题：打开剧集流水线总览）。那里有每阶段的「生成 / 重新生成」「导演审核」，以及每格的「生成这条视频 / 重新生成这条视频」。打开前该资产至少要跑过一次节拍拆解，否则视图是空的。

## 重跑与返工（最容易踩的坑）

- `task_run` **会跳过状态为 done 的节点**。所以「改完参数再 `task_run`」通常什么都不发生：失败/未跑的会被补跑，已成功的不会重跑。这是省钱的默认行为，不是 bug。
- 强制重跑某阶段：在「剧集流水线」视图点该阶段的「**重新生成**」。它会强制重跑该阶段节点，并把该阶段的**全部下游产物（拼图 / 提取 / 视频 / 审核）一并作废**，之后补跑才是一致的。
- 只重跑一条视频：在流水线视图选中该格 → 「重新生成这条视频」，只重跑那一个视频节点，上游全部复用。
- 画布上的整图「运行」**不跳过**已完成节点，会把整条链（含 36 条视频）重跑一遍 —— 不要用它来"补跑"。
- 改了剧本或某个阶段的文本后，必须从该阶段往下整链失效重跑；否则下游产物与新文本不一致（「重新生成」会自动做这件事）。

## 常见追问怎么答

- **「能不能只出 9 条视频？」** 换 short-drama9。不要在 36 条的图里删节点 —— 会破坏格索引与审核状态。
- **「视频时长不对 / 太短？」** `generateDuration` 只是请求值，会被所选视频模型的时长档 clamp。改档位或换模型。
- **「参考图没锁住角色 / 为什么说是首帧？」** 这些视频节点的图是从通用参考图口 `in-image` 进的，作为 image reference 送模型；节点指令里叫它「参考首帧」，那是文案。真正的首帧锁定需要模型声明支持 first_frame，并把 `generateFrameMode` 设为 `first`、改从首帧口接图（此模式下参考图会被弃用）—— 需自行确认所选模型是否支持。最稳的锁外观方式仍是把 9宫格 / 4宫格拼图阶段做对。
- **「审核 FAIL 了怎么办？」** 看流水线视图顶部的 FAIL 原因，重跑被 FAIL 的阶段（原因会自动进提示词）。若 FAIL 的原因是格式（缺列 / 缺格 / 来源标记丢失），改提示词里的格式要求再重跑，比反复重跑更有效。
- **「多集/连续剧怎么办？」** 一次一集；第 2 集再落一份资产（新的 assetId → 新的审核作用域）。
- **「能不能换成别的模型重跑某一阶段？」** 可以：用 `graph_edit` 改该节点（或全部图文视频节点）的 `generateModel`，再按上面的方式强制重跑。文本阶段、图片阶段、视频阶段的 `generateModel` 是同一个参数名。
- **「跑完能删工作流资产吗？」** 产物落在工程里，但节点图与审核状态也在该资产上；删了就不能再单格重跑或做 4 宫格追溯，建议保留。
